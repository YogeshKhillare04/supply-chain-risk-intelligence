# 🚚 Supply Chain Risk & Delivery Intelligence

Predicting late delivery risk using machine learning to help logistics teams identify high-risk shipments before dispatch, understand why delays happen, and make better operational decisions.

---

## Problem Statement

Late deliveries hurt customer satisfaction and increase operational costs. This project uses historical supply chain data to build a model that predicts whether an order is likely to be delivered late — and more importantly, provides a **probability score** and **risk category** so operations teams can prioritize their interventions.

The central question:

> Can historical order and operational data identify orders likely to experience delivery delays, explain the reasons behind those predictions, and support better operational decisions?

---

## Why This Matters

In logistics and food-delivery operations, knowing which orders are at risk of delay BEFORE they're dispatched allows teams to:

- Proactively reroute or prioritize high-risk shipments
- Allocate additional resources during high-demand periods
- Understand which shipping modes, markets, or product categories have the worst delivery performance
- Move from reactive problem-solving to data-driven decision making

The same approach applies directly to food-delivery companies where predicting delivery delays helps with rider allocation, restaurant prioritization, and customer communication.

---

## Dataset

**DataCo Smart Supply Chain Dataset** from Kaggle — 180,519 supply chain transactions with 53 columns covering orders, shipping, customers, products, and financials.

- **Target**: `Late_delivery_risk` (binary: 1 = late, 0 = on time)
- **Class distribution**: ~55% late, ~45% on time (mildly imbalanced)
- **Time range**: 2015–2018
- **Source**: [Kaggle](https://www.kaggle.com/datasets/shashwatwork/dataco-smart-supply-chain-for-big-data-analysis)

See [`data/README.md`](data/README.md) for download and setup instructions.

## Data Preparation

### Cleaning
- Removed PII columns (email, names, passwords) — no predictive value
- Removed identifier columns (order IDs, customer IDs)
- Removed `Order Zipcode` (86% missing)
- Removed `Product Description` (100% missing)
- Dropped duplicate rows
- Extracted date features (year, month, day, day of week, hour)

### Data Leakage Prevention
Three columns were removed because they contain post-delivery information:

| Column | Why it's leakage |
|--------|-----------------|
| `Days for shipping (real)` | Actual shipping time — only known after delivery |
| `Delivery Status` | The delivery outcome — this IS what we're predicting |
| `shipping date (DateOrders)` | When item shipped — not known at order time |

Additionally, aggregated features (category averages, frequencies) are computed from **training data only** and then mapped to the test set. This prevents a subtle form of leakage where the model indirectly sees test data during training.

---

## Feature Engineering

10 engineered features across 3 categories:

**Financial features** (computed per row — no leakage risk):
- `High_Value_Order` — binary flag for above-median order value
- `Discount_Percentage` — discount as % of item value
- `Sales_Per_Item` — average sales per item
- `Profit_Margin` — benefit as % of sales
- `Order_Size` — quantity × price
- `Price_Difference` — gap between product price variants

**Shipping features**:
- `Urgent_Shipment` — flag for scheduled delivery ≤ 2 days

**Aggregated features** (computed from training data only):
- `Category_Avg_Sales` — typical order value for the product category
- `Category_Frequency` — how popular this category is
- `Market_Frequency` — order volume in this market

## Statistical Analysis

Before machine learning, I used statistical tests to check whether the patterns observed in EDA are statistically significant:

| Test | Question | Finding |
|------|----------|---------|
| Chi-square | Is shipping mode associated with late delivery? | Significant — different modes have different delay rates |
| Welch's t-test | Do scheduled days differ for late vs on-time? | Significant difference found |
| ANOVA | Does order value vary across customer segments? | See notebook for results |
| Correlation | Which features linearly relate to the target? | All weak — suggests non-linear relationships |
| Point-biserial | Is order quantity related to delay? | Very weak linear relationship |

**Key insight:** Weak linear correlations across all features strongly suggested that tree-based models would outperform linear models — which they did.

## Machine Learning Approach

### Model Comparison

I compared 6 models, starting from a dummy baseline:

1. **Dummy Classifier** (baseline — always predicts majority class)
2. **Logistic Regression**
3. **Decision Tree**
4. **Random Forest**
5. **Extra Trees Classifier**
6. **Gradient Boosting**

Each model was evaluated on: Accuracy, Precision, Recall, F1, ROC-AUC, and PR-AUC.

The best model was selected based on **F1 score** — balancing catching late deliveries (recall) with avoiding false alarms (precision).

### Probability-Based Risk Categories

Instead of just binary predictions (late/on-time), the model outputs a late delivery probability which is mapped to risk categories:

| Category | Probability | Interpretation |
|----------|-------------|----------------|
| Low Risk | < 0.3 | Model is fairly confident delivery will be on time |
| Medium Risk | 0.3 – 0.7 | Uncertain — could go either way |
| High Risk | ≥ 0.7 | Model is fairly confident delivery will be late |

The threshold analysis notebook explores precision/recall trade-offs at different thresholds.

---

## Error Analysis

I analyzed where the model fails — which is often more informative than where it succeeds:

- **False negatives** (missed late deliveries) tend to be borderline cases with probabilities just below 0.5
- Performance varies by **shipping mode**, **market**, and **order value quartile**
- Some segments are harder to predict than others

This analysis helps identify where to focus improvements and whether different thresholds should be used for different segments.

## Model Explainability (SHAP)

SHAP (SHapley Additive exPlanations) provides two levels of explanation:

1. **Global**: Which features matter most across all predictions?
2. **Individual**: Why did THIS specific order get a high risk score?

SHAP is compatible with Extra Trees (uses TreeExplainer) and shows both the magnitude and direction of each feature's impact.

**Important:** SHAP shows contribution to the prediction, not causation. "Shipping mode contributed to the high risk score" ≠ "Shipping mode caused the delay."

## Forecasting

I explored demand forecasting as a complement to risk prediction:

- Aggregated daily/weekly order volumes from the dataset
- Compared simple baselines (historical average, moving average) with Holt-Winters exponential smoothing
- Evaluated with MAE and RMSE

**Operational relevance:** If we predict high order volume AND many high-risk orders, we can proactively allocate more delivery resources. This is directly relevant to food-delivery operations.

**Limitation:** This dataset isn't real-time operational data, so the forecasting patterns may not reflect actual live conditions.

---

## A/B Test Simulation

I simulated an experiment to demonstrate how you'd validate whether model-based interventions actually improve outcomes:

- **Control**: Normal process (no model)
- **Treatment**: High-risk orders receive proactive intervention
- Statistical significance testing (z-test for proportions)
- Confidence intervals for the treatment effect

**This is clearly labelled as a simulation** — the intervention effect is assumed, not measured. In a real company, you'd run an actual randomized experiment.

## Key Findings

1. **Shipping mode is the strongest predictor** — Standard Class has the highest delay rate and is the most important feature in both tree-based importance and SHAP analysis
2. **Non-linear relationships dominate** — weak linear correlations but strong tree-based model performance confirms this
3. **Risk categories work** — High Risk orders have a significantly higher actual late delivery rate than Low Risk orders
4. **Some markets and categories are harder to predict** — error analysis reveals systematic patterns in model failures

---

## Limitations

1. The DataCo dataset is historical, not real-time — patterns may not reflect current operations
2. External factors (weather, holidays, traffic) are not captured
3. Aggregated features could become stale if category/market distributions shift
4. The A/B test is simulated, not a real experiment
5. Forecasting uses coarse weekly granularity — real food-delivery would need hourly/zone-level
6. No hyperparameter tuning was performed — default parameters may not be optimal
7. The model assumes the same leakage-free features would be available in production
